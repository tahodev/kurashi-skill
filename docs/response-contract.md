# 共通レスポンス契約

複数のスキルを同じ会話で使っても、データの出所と新しさを見失わないための共通表示ルール。各 `SKILL.md` が正本であり、この契約は**取得結果をユーザーへ伝えるときの共通の枠**を定める。

## 必須フィールド

すべての照会結果に、次の5項目をこの順序で添える。値が取れない項目も省略せず、「不明」と理由を書く。

| 項目 | 書く内容 |
|---|---|
| 対象 | 都道府県、市区町村、予報区、緯度経度など、結果が適用される地域・地点。全国データや地域に依存しない計算は「全国」「地域指定なし」などと書く |
| データ時刻 | 情報の発表時刻またはデータ更新日。予報の対象時刻や統計の基準時点が別にある場合は併記する |
| 照会時刻 | 実際に取得した時刻。タイムゾーンを必ず付ける (日本向けの既定は JST) |
| 出所 | 機関名と公式URL。「公式」か、公式情報を使った計算・変換かを明記する |
| 不確実性 | 未確認、欠損、解像度、更新遅延、推定、対象外、取得失敗など。特になければ「既知の制約: なし」と書く |

## 表示テンプレート

```text
[結果]
対象: <地域・地点>
データ時刻: <発表・更新時刻> (対象時刻: <必要な場合>)
照会時刻: <YYYY-MM-DD HH:mm タイムゾーン>
出所: <機関名>・公式 <URL> | <公式データ / 公式データを使った計算>
不確実性: <制約、欠損、推定、または「既知の制約: なし」>
```

結果が複数ある場合は、各結果に同じ5項目を付ける。発表時刻が異なるデータを、ひとつの「最新時刻」にまとめない。

```text
[天気予報]
対象: 東京都東京地方
データ時刻: 2026-09-19 05:00 JST (対象: 9月19日)
照会時刻: 2026-09-19 07:10 JST
出所: 気象庁・公式 https://www.jma.go.jp/bosai/forecast/
不確実性: 予報は今後更新される

[雨雲]
対象: 東京駅付近 (取得タイルの中心座標 ...)
データ時刻: 2026-09-19 07:05 JST (実況)
照会時刻: 2026-09-19 07:10 JST
出所: 気象庁・公式 https://www.jma.go.jp/bosai/nowc/
不確実性: タイル画素による地点判定。色から読んだ雨量強度は目安
```

上の日時・場所は表示例であり、実際の回答には取得した値を入れる。

## 時刻の選び方

1. APIに発表時刻 (`reportDatetime` など) があれば、それを使う。
2. 発表時刻がなく更新日のみなら、更新日を使い時刻を作らない。
3. ファイル単位と自治体単位の更新日がある場合は、回答対象に近い自治体単位を優先する。
4. HTTPヘッダーやローカル保存時刻を、データ発表時刻の代わりにしない。
5. 日時を取得できない場合は「不明 (配信データに時刻なし)」と書く。

## 公式性の表し方

- 行政機関が配信する原データ: `公式データ`
- 公式データをこのスキルの手順で集計・距離計算・暦変換した値: `公式データを使った計算`
- 公式の対応表を確認できず、画素色などから判定した値: 公式データであっても、判定部分は `推定` と不確実性に書く

「公式」は正確さや即時性の保証ではない。緊急時は元の公式ページと自治体の発表も案内する。

## 失敗・部分成功

- 取得失敗を「該当なし」「警報なし」「雨なし」に読み替えない。
- 複合照会の一部だけ失敗した場合、取得できた結果は表示し、失敗した結果にも対象・照会時刻・出所・失敗理由を書く。データ時刻は「取得できず不明」とする。
- キャッシュや前回値を使う場合は、データ時刻と「最新取得ではない」ことを不確実性に書く。
- 異なる地域粒度のデータを組み合わせる場合、それぞれの対象範囲を保つ。


## 取得時の落とし穴チェックリスト

各スキルの「エラー・失敗時の対応」に書く前に、共通で見るべき罠。新しいスキルを実測するときはこの順で確認する。

1. **存在しないURLでも200が返るSPA**: シェルHTMLが返って404にならない。受け取った本文の先頭(ヘッダ行・JSONの型)が期待の形式かを必ず確認する(例: air-quality)。
2. **URLを推測しない**: 似た名前のファイル(marinevolcano.json、amedastation.json など)は404になりがち。URLはサイトの案内か実測で確かめる(例: volcano、amedas-weather)。
3. **未解除・旧版のデータが残り続ける**: 解除されなかった警報が配信JSONに残る(volcano の2007年エントリ)、検索で旧版データセットが上位に来る(shelter-lookup のP20)。必ず発表日時・版を確認して引用する。
4. **空の配列・ヘッダのみのCSVはエラーではない**: 「現在発表なし」の正常値。失敗と読み替えない(bosai-alert、amagumo、air-quality の alert.csv)。
5. **CSVの方言**: フィールド内の改行を含む引用符つきレコード(shelter-lookup)、ヘッダや値の前後空白(heatstroke の地点マスタ)、`欠測;` や `-` の欠測記号。行数とパース結果がずれたらまず方言を疑う。
6. **観測所・地点ごとに測れる項目が違う**: 同じAPIでも地点タイプで返る要素が変わる(amedas-weather、air-quality)。欠損は「その地点では測っていない」と伝え、推測で埋めない。
7. **ID系がJISコードとは限らない**: 都道府県らしきパラメータが独自のブロック番号体系のことがある(heatstroke の pref_cds)。既知の地点で往復テストしてから使う。
8. **HTTPステータスを見て終わらない**: 200でも本文がエラーJSON(`status: "error"`、e-Stat の `STATUS=100`)のことがある。本文のステータスフィールドを必ず見る。

## English labels

For English responses, use the same order: `Target`, `Data issued/updated`, `Queried at`, `Source and official status`, `Uncertainty`. Never omit an unknown field; state `unknown` and why.
